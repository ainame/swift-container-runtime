# kontainer-runtime parity checklist

The goal is feature parity with the behavior implemented by [kontainer-runtime at 357b8f2](https://github.com/ternbusty/kontainer-runtime/tree/357b8f295a7fad450c822c61e79cf22f75546640). runc is the behavioral authority when the implementations differ. This checklist records the target's actual code paths, rather than assuming that a decoded schema field or a compatibility-test name proves working behavior. The [roadmap](roadmap.md) orders the implementation; completing one phase does not complete this checklist.

## Commands

| Surface | Target behavior | Swift status |
| --- | --- | --- |
| `run` | Bundle, foreground wait/status/cleanup, detach, keep, PID file, console socket, pidfd socket, no-pivot | Foreground, detached, keep, PID file, `--preserve-fds`, and `--pidfd-socket` (label `standard`; empty value rejected) implemented; console socket option missing |
| `create`, `start`, `state`, `kill`, `delete`, `list` | Persistent transitions and process identity; named/numeric signals; kill-all; force deletion; table/JSON/quiet listing | Core lifecycle and create PID files implemented; kill-all without a private PID namespace and optional flags remain missing |
| `pause`, `resume` | Cgroup freezer | Implemented with completion checks, kernel-derived paused state, identity protection, and Linux workload tests against runc |
| `update` | Resources file or stdin; individual resource flags; memory check-before-update | Implemented for supported memory/pids/CPU/cpuset fields, with saved merge semantics and Linux comparisons; other resource fields/flags remain, and failed-update rollback differs as documented in README |
| `events` | Stats snapshot or interval stream, OOM events, termination on deletion | Implemented for cgroup v2: runc's fs2 stats fields and units (CPU, throttling, memory/swap, raw `memory.stat`, pids, PSI, io byte/operation tables, hugetlb), Go-duration `--interval` (default 5s), OOM events independent of the interval, stream end on cgroup exit or state deletion/recreation. `intel_rdt` and `network_interfaces` keep runc's empty `{}`/`null` (kontainer-runtime has no Intel RDT support and runc's network list is deprecated and always empty). OOM events report each `oom_kill` increase rather than every `memory.events` change, and out-of-range intervals are rejected |
| `ps` | Table/JSON output and verbatim trailing host `ps` arguments | Implemented, including descendant/threaded groups, lifecycle states, empty JSON null, and host-table filtering; compared with runc |
| `exec` | Command or process JSON; detach, terminal, console/PID/pidfd; cwd, env, user/groups, capabilities, preserved FDs, sub-cgroup, ignore-paused | Command and standalone process JSON forms implemented: existing namespaces/root/cgroup, foreground status, detach, PID files, cwd/env/numeric user overrides, appended `--additional-gids` (each given group once; runc 1.4.0-0ubuntu1 appends a lone group twice), bare `--no-new-privs`, repeatable `--cap` (ambient only where inheritable, unknown names rejected), configured process setup, runc-style `args[0]` lookup in the process PATH. `--ignore-paused` waits for resume before forking (as kontainer-runtime; runc forks into the frozen cgroup), failing if the container is deleted or replaced. `--preserve-fds N` passes caller descriptors 3..2+N, rejecting holes and close-on-exec descriptors before any state exists (runc passes any open descriptor and ignores negative counts); compared with runc in `scripts/preserve-fds-integration.sh`, which covers `create` and `run` too. `--pidfd-socket` sends label `setns`, compared with runc in `scripts/pidfd-socket-integration.sh` (also `create`/`run`). Terminals, `--no-new-privs=false`, socket activation, and sub-cgroups remain. Linux comparisons cover basic behavior; the detailed exec security matrix remains |
| `spec` | Generate default `config.json`; bundle and rootless options | Implemented as a generator following runc defaults, with runtime hostname and exclusive creation; its starter still requests runtime features listed below as missing |
| `features` | OCI feature JSON matching actual runtime support | Implemented; reports only currently implemented build features, with unsupported surfaces empty or disabled |
| Global options | State root, log path, text/JSON logs, debug | State root implemented; logging missing |
| Version | Runtime version, commit, OCI specification version; `--version`/`-v` | Implemented with an explicit development version and OCI version; no commit line when build provenance is unknown |

Evidence: target `Main.kt`, `command/*.kt`, `state/State.kt`, and `config/KontainerConfig.kt`.

## OCI configuration and runtime behavior

| Area | Remaining target behavior |
| --- | --- |
| Process setup | HOME resolution; empty/omitted-process behavior; rlimits with `exec`; OOM score; scheduling, I/O priority, CPU affinity |
| Namespaces | Join supplied namespace paths; host/shared combinations; user, cgroup, time namespaces; UID/GID mapping handshake and mapping-helper fallback; time offsets |
| Rootfs and mounts | No-pivot; sysfs, mqueue, shm and cgroup mounts; bind/rbind/remount and propagation; recursive attributes; idmapped mounts; custom character/block/FIFO devices with ownership/mode; sysctl |
| UTS and networking | Domainname; loopback setup; moving and renaming host interfaces. Hostname and new, unconfigured network namespaces already exist |
| Cgroup v2 | Only a subset is implemented: `linux.cgroupsPath`, memory `limit`/`reservation`/`swap`/`checkBeforeUpdate`, pids `limit`, CPU `shares`/`quota`/`period`/`burst`/`idle`/`cpus`/`mems`, adoption of one supplied path by at most one concurrent container, and cleanup at delete and on failure (see README). Still missing: memory `swappiness`/`kernel`/`kernelTCP`/`disableOOMKiller`/`useHierarchy`; CPU `realtimeRuntime`/`realtimePeriod`; hugepages; unified controls; block-I/O weight/throttles; network and RDMA; device BPF; update flags for unimplemented resources; removal of created ancestor cgroups; and sub-cgroups for `exec`. These fields are rejected, not ignored. |
| Security | Capabilities with `exec`; AppArmor/SELinux execution-context staging and availability behavior; session keyrings; sealed executable handoff |
| Seccomp | Actions, architectures, argument comparisons, conditional rules, flags, notification listener handoff |
| Hooks | All six phases, environment, state on stdin, timeout and failure semantics |
| Foreground and descriptors | Signal forwarding, terminal I/O/resizing, console handoff, socket activation (`LISTEN_FDS`). Inherited descriptors from 3+N up are marked close-on-exec; `--preserve-fds N` is implemented |
| Portability and integration | arm64 and x86_64 Linux; real musl/static build and execution; applicable runc compatibility tests; containerd/go-runc interactions |

The current foreground and persistent lifecycle subset has real Linux debug/release evidence for PID 1, pivoted rootfs, proc/tmpfs/devpts, standard devices, hostname, cwd, explicit environment, stdio, status propagation, rejected configurations, descriptor cleanup, lifecycle transitions, concurrent create/start, signal delivery, stale process identity protection, and failure cleanup. Process credentials (uid, gid, additional groups including clearing, umask with runc's default, and no-new-privileges) are compared with runc from inside the workload in foreground, detached, and create/start modes; credentials with `exec`, user-namespace mappings, and `/proc/self/setgroups` deny handling remain. The five capability sets (absent, `{}`, configured root and non-root with ambient and no-new-privileges, and an inherited inheritable capability kept outside a reduced bounding set) are compared with runc through `/proc` masks and allowed/denied operations in the same three modes, and a set the kernel refuses fails under both; this runtime rejects the unknown names, kernel-unsupported numbers, and ambient requests runc only warns about. Rlimits (absent, configured root and non-root, repeated types applied in order, raised hard limits, and infinity) are compared with runc in the same three modes, both through the workload's `getrlimit` values and through the created init's `/proc/PID/limits` right after `create`. `RLIMIT_NOFILE`, `RLIMIT_FSIZE`, and `RLIMIT_CPU` enforcement is compared too, and refused, invalid, and unknown entries must fail under both without leaving state or processes. A waiting init's `RLIMIT_NOFILE` is the one value not compared, and only when the config omits it (even if it configures other rlimits), because runc's Go bootstrap raises it until `execve`. Its workload's value is compared. With tiny `RLIMIT_NOFILE` and `RLIMIT_AS`, both runtimes must hold and enforce the limits and clean up. Whether each runtime's own bootstrap fits under them is recorded rather than required to match, since that reflects runtime overhead rather than OCI semantics. Deliberate differences: a missing `soft`/`hard` is rejected (runc decodes 0), and soft above hard is rejected before launch (runc fails at `prlimit`). Read-only roots are verified against runc with exact EROFS checks, writable child mounts, created-init mount flags, and unchanged host contents and mount permissions in Linux debug/release. This runtime also preserves inherited root mount security flags. Masked and read-only paths are compared with runc as root and uid 1000 in the three modes, with and without `root.readonly`, through exact errno names, contents, device numbers and inode identity, created-init mount tables, and host isolation. `readonlyPaths: ["/"]`, configurations without `/proc`, and all-missing paths are compared too. Deliberate differences: paths with `.`/`..` components are rejected (runc cleans them lexically), magic links fail with `ELOOP` (runc follows them), a mask its path does not show (such as one on `/`) fails setup, and read-only paths need Linux 5.12+ for `mount_setattr`. Setup assumes a single owner of the rootfs; it is not race-free against a concurrent host writer. It does not establish the remaining behavior above.

Evidence paths in the target, relative to `src/nativeMain/kotlin/`:

- Process: `spec/Spec.kt`, `process/InitProcess.kt`, `process/ProcessSecurity.kt`, `process/{HomeResolver,Scheduler,IOPriority,CpuAffinity}.kt`, `command/Exec.kt`.
- Namespaces: `command/Create.kt`, `process/MainProcess.kt`, and `src/nativeInterop/cinterop/bootstrap/bootstrap.c` (the last path is relative to the repository root).
- Mounts/network: `rootfs/Rootfs.kt`, `process/InitProcess.kt`, `process/MainProcess.kt`, and native network interop.
- Resources: `cgroup/{CgroupV2,DeviceCgroup}.kt`, `command/Update.kt`.

## What is not evidence of a parity requirement

The target mentions checkpoint/restore in help names but does not register or implement those commands. Its `--systemd-cgroup` option explicitly reports that it is unimplemented, and its resource implementation uses cgroup v2. Checkpoint/restore, cgroup v1, and systemd-managed cgroups are therefore outside this target's implemented functionality.

Likewise, `linux.mountLabel` and `blockIO.leafWeight` appear in its schema without applying consumers. AppArmor and SELinux have staging code while its feature report says they are disabled; parity needs platform-aware availability and error tests rather than an unconditional support claim.

A feature becomes complete only after its implementation and relevant observable behavior have been checked. Passing a narrow fixture or matching a CLI name is not full feature parity.
